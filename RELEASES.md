# Release Engineering Policy

ZeroTrust-FL-Sim uses Semantic Versioning for public releases. The project remains pre-1.0 until the stable gates in `ROADMAP.md` are satisfied.

## Channels

- `0.x.y` — development releases; compatibility may change with documented migration notes
- `x.y.z-alpha.N` — feature integration and early validation
- `x.y.z-beta.N` — feature-complete candidate undergoing compatibility/security validation
- `x.y.z-rc.N` — release candidate; only release-blocking fixes should change behavior
- `x.y.z` — stable release

## Required release evidence

Every stable release should be traceable to one immutable source commit and include or link to:

- source archive
- changelog/release notes
- exact version and commit SHA
- supported platform/toolchain matrix
- test and integration status
- benchmark methodology when performance claims are made
- checksums for downloadable artifacts
- SBOM for shipped binaries/images once the supply-chain milestone is complete
- signatures and build provenance once signing/provenance automation is complete

## Release gates

A release cannot be promoted when a required check is failing or skipped without an explicit documented exception. Stable releases require:

- Go format, vet, and tests
- Python lint and full tests
- C++ native extension build and tests
- privacy/CKKS tests for the supported build profile
- Docker zero-trust cluster startup and benchmark smoke integration
- dashboard typecheck/build when dashboard code changed
- no committed private keys, generated production credentials, or secrets

Additional security, packaging, Kubernetes, fuzz, chaos, SBOM, signing, and provenance gates become mandatory at the roadmap milestones that introduce them.

## Artifact integrity

Published OCI images and packages should be referenced by immutable version/digest in production examples. Mutable `latest` tags may exist for convenience but are never sufficient evidence for a reproducible experiment or production deployment.

## Signing and provenance target

The v1 supply-chain target is keyless or hardware-backed artifact/image signing, machine-readable SBOMs, and verifiable build provenance generated by trusted CI. These are engineering targets; the repository must not claim SLSA, OpenSSF, NIST, FIPS, ISO, SOC, or other certification merely because controls are inspired by those frameworks.

## Rollback and withdrawal

A release with a critical security or data-integrity defect may be marked unsupported/withdrawn in release notes. The immutable tag/history is retained for auditability; fixes ship as a new version. Users should never be instructed to replace an existing release artifact in place.
