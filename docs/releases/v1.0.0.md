# ZeroTrust-FL-Sim v1.0.0

Release date: 2026-09-08

ZeroTrust-FL-Sim v1.0.0 is the first stable release of the supported federated-learning simulation and security-resilience profile. The release candidate is required to pass the complete repository CI, Security, Deployment Validation, Docker integration, durable recovery, benchmark/reproducibility, and real Kind/Kubernetes evidence gates on the exact release commit before the v1.0.0 tag is created.

## Supported production profile

The supported aggregation path is CPU/PyTorch/native C++ using the validated PyTorch CPU and C++20 Byzantine-robust aggregation implementations. The supported deployment evidence covers the Go coordinator, Python/PyTorch workers, durable PostgreSQL/S3 recovery, immutable OCI images, Docker integration, and Helm deployment to an ephemeral Kind/Kubernetes cluster with CI-only PKI.

CUDA remains experimental and unvalidated in v1.0.0. A real eligible CUDA device must execute `scripts/capture_cuda_parity_evidence.py` and produce reviewed evidence before CUDA can be described as a validated release profile. CPU-only or skipped CUDA tests are not CUDA validation.

## Major release capabilities

- Zero-trust worker enrollment and authenticated coordinator communication with explicit identity and lifecycle controls.
- Replay defenses, bounded model/update validation, protocol compatibility checks, and rate controls.
- Non-IID federated-learning simulation with malicious-client and attack scenarios.
- PyTorch reference aggregation and C++20 native Byzantine-robust aggregation with CPU parity coverage.
- Differential-privacy and CKKS paths with explicit claim boundaries.
- Durable PostgreSQL/S3 state, experiment/configuration fingerprints, model identity persistence, backup, and clean-room recovery.
- Stable Python SDK API v1 and the `ztfl` operator CLI.
- Docker and Helm/Kubernetes deployment profiles with security-context, NetworkPolicy, probes, resource, and recovery validation.
- Reproducible benchmark manifests tied to exact commits and runtime facts.
- Dependency, license, SAST, secret, fuzz, container vulnerability, SBOM, signing, and provenance controls.
- Signed source and OCI release evidence produced by the tag workflow.

## Security and trust boundaries

The coordinator enforces authenticated enrollment, registration lifecycle controls, replay defenses, explicit protocol/model/schema identity, bounded update payloads, durable experiment identity, and durable model identity. Durable state schema v3 fails closed when persisted `model_id` does not match runtime configuration.

Byzantine-robust aggregation remains subject to each algorithm's documented population and adversary bounds. Differential privacy depends on the configured mechanism and accounting parameters. CKKS is a separate implemented path; the ordinary gRPC update path must not be described as end-to-end homomorphically encrypted.

## Owner-authorized assurance exceptions

The repository owner explicitly authorized publication of v1.0.0 on 2026-09-08 with three external/administrative assurance items waived rather than falsely marked satisfied. These waivers are recorded in `release/v1.0-evidence.json` and do not convert missing evidence into completed assurance.

- #37 — GitHub `main` branch protection is not enabled at release time. Required-check enforcement, force-push blocking, and branch-deletion blocking therefore are not technically enforced by GitHub. The v1.0.0 release candidate still must pass the complete PR and exact-release-commit workflow gates before tagging.
- #70 — v1.0.0 is **not independently security assessed**. Repository-owned CI, SAST, dependency auditing, secret scanning, fuzzing, container vulnerability scanning, recovery testing, and Kubernetes evidence are extensive but are not a substitute for an external assessment. Do not represent v1.0.0 as independently audited or security certified.
- #73 — no OpenSSF Best Practices project/application record or badge is claimed for v1.0.0. OpenSSF Scorecard automation and repository security controls exist, but they do not constitute a completed Best Practices application.

These exceptions are release-governance decisions, not technical evidence. Downstream users with policies requiring protected default branches, independent security review, or an OpenSSF Best Practices badge should treat those requirements as unmet for v1.0.0.
